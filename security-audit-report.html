TALENT-MAIN — Security Audit Report

Static security review of the TALENT education platform — a Next.js 16 (App Router) + Prisma 7 / SQLite application with AI-driven quiz extraction, S3 file uploads, transactional email, and role-based teacher / student / admin access.

Branch dev Commit 2453a51 Date 2026-06-21 Routes reviewed 70 API endpoints Method Manual code review + dependency scan

01Executive summary

The codebase demonstrates a solid baseline security posture: passwords are bcrypt-hashed (cost 12), secrets at rest are encrypted with AES-256-GCM, database access is fully parameterized through Prisma (no SQL injection surface), and the great majority of API routes enforce role and resource-ownership checks. The most material risks are two broken-object-level-authorization (IDOR) endpoints, a real password committed to version control in a demo seed, and the absence of rate limiting, HTTP security headers, and dependency patching.

03Scope & methodology

This review covered the full repository on the dev branch (commit 2453a51), which is the integration branch ahead of main. Areas examined:

  • Authentication & session — NextAuth v5 (Credentials provider), JWT sessions, bcrypt hashing, signup-token gating.
  • Authorization — all 70 src/app/api/**/route.ts handlers, the src/proxy.ts middleware, and ownership helpers (quiz-access.ts).
  • Data handling — Prisma queries (SQL-injection surface), input validation, file uploads to S3, AI prompt construction.
  • Secrets — env handling, encryption at rest (crypto.ts), committed-secret scan across tracked files.
  • Infrastructure — Dockerfile, entrypoint, GitHub Actions workflows, dependency manifest.

Methodology: manual source-code review of the checked-out dev tree, augmented by npm audit for dependency CVEs and a regex scan for committed credentials. Dynamic testing, fuzzing, and live exploitation were out of scope.

05Detailed findings

High F-01 Real password committed to version control

prisma/seed-demo.ts:10–16

The demo seed script hard-codes a genuine-looking password and a real @uga.edu email address, then creates a TEACHER account from them. The password is now permanently in git history.

const hashedPassword = await bcrypt.hash("nY*H1#6i#t8kqeP", 12);
const user = await prisma.user.upsert({
  where: { email: "edwardcheng@uga.edu" },
  create: { email: "edwardcheng@uga.edu", role: "TEACHER", hashedPassword, ... },
});

Impact

If this individual reuses the password elsewhere, it is exposed. If seed:demo is ever run against a production database, it provisions a known-credential teacher account. Secrets in git history persist even after deletion.

Recommendation

Remove the literal password — read it from an env var (e.g. DEMO_TEACHER_PASSWORD) or generate a random one and print it once. Rotate the password if it is used anywhere real. Guard the demo seed so it refuses to run when NODE_ENV=production. Consider scrubbing it from history (BFG / filter-repo) for the affected account.

High F-02 IDOR — any authenticated user can read any class

src/app/api/classes/[id]/route.ts — GET

The handler authenticates the caller but performs no ownership or enrollment check before returning the full class record — including every enrollment, the joined student.user objects (names and email addresses), and active invitations. Any logged-in user (any teacher, or any student) can read any other class by iterating the id.

export async function GET(_req, { params }) {
  const session = await auth();
  if (!session?.user) return ...401;        // authenticated…
  const { id } = await params;
  const cls = await prisma.class.findUnique({  // …but NO ownership check
    where: { id },
    include: { enrollments: { include: { student: { include: { user: true } } } },
               invitations: { ... } },
  });
  return NextResponse.json(cls);
}

Impact

Broken object-level authorization leading to disclosure of student PII (names, emails) and roster/invitation data across tenant boundaries. Note the sibling PATCH/DELETE on the same route do verify ownership via getTeacherClass() — only GET is missing the check.

Recommendation

Apply the same ownership/enrollment gate the mutating verbs use: for a TEACHER, confirm class.teacherId === teacher.id; for a STUDENT, confirm an enrollment exists; otherwise return 404. Reuse the existing getTeacherClass() helper.

Medium F-03 IDOR — class quiz assignments readable for any class

src/app/api/classes/[id]/quizzes/route.ts — GET

Same pattern as F-02 at lower sensitivity: the GET handler checks only that the caller is authenticated, then returns every classQuiz (with quiz titles, topics, question counts) for the supplied class id. The POST on this route correctly gates on teacher ownership; the GET does not.

const session = await auth();
if (!session?.user) return ...401;
const classQuizzes = await prisma.classQuiz.findMany({ where: { classId: id }, ... });
return NextResponse.json(classQuizzes);  // no ownership/enrollment check

Impact

Authenticated cross-class disclosure of quiz/curriculum metadata. Lower severity than F-02 (no direct PII), but the same authorization gap.

Recommendation

Gate on teacher ownership or student enrollment before querying, consistent with the rest of the class API surface.

Medium F-04 No rate limiting on authentication & invitation endpoints

api/auth/register · api/auth/admin/register · api/invitations/[token] · api/invitations/[token]/lookup

No request throttling exists anywhere in the application. Sensitive endpoints can be hit at unlimited speed.

Impact

  • Login / signup — password brute force and signup-token guessing (the token is the only gate on teacher/admin registration).
  • Invitation lookup — enumeration of valid invitation tokens and student "81 numbers" (org-defined IDs) used for roster matching.

Recommendation

Add IP- and account-scoped rate limiting (e.g. a fixed/sliding-window limiter, or middleware-level throttling) to the auth, registration, and invitation routes. Add a short lockout / exponential backoff after repeated failures.

Medium F-05 Missing HTTP security headers

next.config.mjs · src/proxy.ts

Neither next.config.mjs (no headers() function) nor the proxy.ts middleware sets any response security headers. Absent: Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy.

Impact

Reduced defense-in-depth: increased exposure to clickjacking, MIME sniffing, mixed-content/downgrade, and a weaker last line of defense against XSS.

Recommendation

Add a headers() block in next.config.mjs (or set headers in proxy.ts) applying a strict CSP, HSTS (max-age ≥ 1 year + includeSubDomains), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, and a sane Referrer-Policy.

Medium F-06 Vulnerable transitive dependencies

package-lock.json — see §06

npm audit reports 13 vulnerabilities (2 high, 9 moderate, 2 low), predominantly in transitive build/runtime dependencies. The two high-severity items — undici (TLS certificate-validation bypass via SOCKS5 ProxyAgent; cross-user cache disclosure) and picomatch (ReDoS / method injection) — are most relevant.

Recommendation

Run npm audit fix, and where fixes are gated behind a major bump, pin patched versions via overrides in package.json. Prioritize undici and picomatch. The repo already routes Dependabot PRs to dev — keep that cadence and merge security bumps promptly.

Low F-07 No CSRF tokens on state-changing routes

all mutating src/app/api/** handlers

State-changing endpoints rely solely on the session cookie with no anti-CSRF token. NextAuth protects its own /api/auth/* routes, and its default SameSite=Lax session cookie blocks most cross-site form posts, which substantially mitigates this.

Recommendation

Confirm the session cookie is SameSite=Lax (or Strict) and that no sensitive state change uses a top-level GET. For defense-in-depth, add an origin/double-submit-token check on mutating routes, or validate the Origin/Sec-Fetch-Site headers in middleware.

Low F-08 Production authentication on a beta dependency

package.json — next-auth ^5.0.0-beta.31

The application's authentication layer depends on a pre-release (beta) of NextAuth v5. Beta releases may carry undisclosed bugs and breaking changes, and Dependabot is configured to ignore major bumps for it.

Recommendation

Track the NextAuth v5 stable release and plan an upgrade. Until then, watch the project's security advisories and pin to the latest beta patch.

Low F-09 No centralized request-schema validation

src/app/api/** (e.g. questions, materials, pdf-extractions)

Request bodies are validated with hand-rolled per-route checks rather than a schema library (zod/valibot). The existing checks are reasonable, but ad-hoc validation is easy to under-apply on new routes and harder to keep consistent.

Recommendation

Introduce a schema validation layer and parse every req.json()/formData() payload through it, rejecting unknown/oversized inputs uniformly. This also reduces the surface for type-confusion and oversized-payload issues.

Info F-10 Destructive Prisma push at container boot

docker/docker-entrypoint.sh:36

The entrypoint runs prisma db push --accept-data-loss on every start. This can drop columns/tables to match the schema without a migration trail.

Recommendation

For production, prefer versioned prisma migrate deploy over db push --accept-data-loss so schema changes are reviewable and non-destructive. The boot-time DB restore staging is otherwise well-handled.

Info F-11 Single static key for all encryption-at-rest

src/lib/crypto.ts

API-provider keys, SMTP passwords, and WebDAV passwords are all encrypted with AES-256-GCM under one API_KEY_ENCRYPTION_SECRET. The implementation is correct (per-record IV + auth tag, strict 32-byte key), but it is a single point of failure with no rotation path.

Recommendation

Document and support key rotation (versioned key id stored alongside ciphertext), and store the master key in a managed secrets service (AWS Secrets Manager / KMS) rather than a plain env var where feasible.

07Security strengths

The following controls were verified and are working well — they should be preserved through future changes.

  • Password storage — bcryptjs at cost 12; constant-time bcrypt.compare; no plaintext storage.
  • Secrets at rest — AI/SMTP/WebDAV credentials encrypted with AES-256-GCM (per-record IV + auth tag) in crypto.ts, and masked on read (only last 4 chars returned).
  • No SQL injection — all queries go through Prisma's parameterized API; the only raw SQL is hardcoded PRAGMA tuning, and the backup path is single-quote-escaped.
  • File uploads — S3 presigned PUT URLs (1-hour expiry), deterministic sanitized keys (no path traversal), .pdf-only enforcement, and configurable size limits.
  • Authorization — admin routes uniformly check role === "ADMIN"; teacher/student routes verify resource ownership/enrollment (including the dev-only student-roster routes, which correctly gate on teacher + class ownership). F-02/F-03 are the isolated exceptions.
  • AI prompt safety — prompts are assembled from database values, not raw user text; no eval, Function, or child_process anywhere in the source.
  • Invitation flow — tokens are validated for active/expiry/max-use and require a roster (81-number) match; only STUDENT role may enroll.
  • No committed secrets — scan for AWS keys, OpenAI keys, and private keys across tracked files came back clean (only a test fixture string); .env/.env.* are git-ignored.
  • Container hardening — multi-stage Docker build runs as a non-root nextjs user; build tools stay out of the final image.
  • CI hygiene — correct pull_request_target usage (no untrusted code execution); least-privilege workflow permissions; Dependabot routed to dev for review; admin self-deletion is blocked.
  • The one dangerouslySetInnerHTML (math-text.tsx:125) renders KaTeX output from DB-sourced math, not arbitrary user HTML — low risk; keep KaTeX patched.
